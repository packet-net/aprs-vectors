Ruling for all libraries (final check, both reviewers raised it): the vectors README Read-back rule already says "A held field read back under the header written is compared with the held data down to the level the held data reached", and "if the field reads as other data under the header written, the refusal is not-encodable". That applies to EVERY packet writer (line, frame, KISS, and a third-party inner packet at every depth), not only when a Mic-E data type or destination is involved. So where your API lets a program hold a packet whose decoded data, header or information bytes no longer agree (changed in place, by copy-with-changes, or built by hand), the writer must decode the held information field under the header it writes and compare with the held data, and refuse not-encodable on any difference: a position whose latitude was changed, an inner packet whose destination was changed at depth 1 or 2, changed status text, changed raw bytes. Compare exactly for a packet that came from a decode; use the read-back's normal comparison with its rounding allowance only for a packet the library built from data (it holds values as given). It must not over-refuse: every packet decoded from bytes and written back unchanged is written exactly as before (prove it by decoding every `tnc2` and `ax25_hex` input in the vectors cases, writing each back as a line and as a frame, and diffing against the output of your current head: zero differences). Never substitute a computed destination or any decoded value for one that was given: refuse. The refusal message must name the real cause (data and information field disagree; not "a Mic-E report is made by its own destination" unless that is it). If your packet type is immutable and has no way to hold disagreeing data, say so and add a test that shows it.
