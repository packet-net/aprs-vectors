Second-review findings for aprs-c (verdict: merge after fixes; all first findings confirmed fixed; no wrong data from honest input in about 150 hostile inputs). Fix all.
1. altitude_in_comment (pdn_aprs.h:744, honoured at encode.c:1603, comparison keyed on it at equal.c:189). The flag itself stays (it is public, documented, and records that decoded data came from a /A=), but a program can set it with a value a /A= does not hold exactly: Mic-E altitude 1000.4 ft with the flag at 1 writes /A=001000. The rule: a /A= is used only where it holds the value exactly; otherwise the Mic-E bytes (nearest metre), or refuse if neither form holds it. Enforce exactness when the flag is set, and make the comparison independent of what the decode says about the form. Document in the header what the flag does and does not do.
2. The 16-bit as_received mark can be collided: decode `}G4ABC>APZ001:>hello` (mark 34137), edit the inner bytes to `>a\x01b%06ld` until the mark matches (63,754 tries), and pdn_aprs_encode_tnc2 writes an inner packet with a control-character warning. Widen the mark to at least 32 bits with a decent mix (for example FNV-1a 32 or 64 over the inner bytes, never zero), state the struct size change, and say in the header and CHANGELOG exactly what it is: a guard against accidental edits, not against a program that sets it on purpose.
3. Third-party nesting past the fourth level through the library API gives does-not-read-back; the rule's code is invalid-third-party-header (only the dump tool gives it today). Repro inner bytes: `A>B:}A>B:}A>B:}A>B:}A>B:>hi`.
4. Docs say "one at the very end is carried" in five places (header encode_tnc2/write_tnc2, README:104 and :189, CHANGELOG:30); the code and the vectors README carry a whole trailing run. Fix the words.
5. The signature change of pdn_aprs_write_tnc2/_ax25 contradicts pdn_aprs.h:25, which promises source compatibility for 1.x. The owner has decided this release is 1.3.0 and that there are no users yet, so keep the change, but make the promise true: reword it to say that 1.3.0 changed these two signatures (and anything else this branch changed incompatibly: list them), and that source compatibility within 1.x holds from 1.3.0 on. Same statement at the top of the CHANGELOG entry.
6. Unrecognized data with an invalid source gives invalid-address although not-encodable is first in the order: check the README at the pin (builder sentence versus order) and follow it; tell me if it is ambiguous. A station path ending in a comma ("WIDE1-1,") is accepted silently while an empty entry in the middle is invalid-address: refuse both the same way.
