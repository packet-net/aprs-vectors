1. An inner third-party header fault comes before any deeper data fault (must fix; about 10 faults lines per seed, 1 data line)

When the first inner packet's header is invalid (a path such as ["TCPIP","G4ABC*"] with an unmarked entry before a used one, ["TC+IP*"], or no destination) and the data one level further down has a fault of its own, you report the deeper data's code (invalid-character, invalid-timestamp, invalid-message-id, invalid-addressee, symbol-mismatch, field-not-allowed, text-reads-as-field, information-field-too-long, not-a-number). The other five give invalid-third-party-header.

Rule: README Refusal reasons, "the refusal names the first code that applies in this order: not-encodable; invalid-address, invalid-path, invalid-third-party-header; invalid-addressee, ...", and "A header given that no form can be (... a bad third-party header) comes first"; Read-back, "Every rule check applies to a third-party packet's inner data, at every depth, exactly as to top-level data". The order runs over the whole record, every depth together.

Fix: check every inner header at every depth (within the four levels) before any data check at any depth; only not-encodable for undecoded inner data comes before them.

2. Dump tool: undecoded data beyond the fourth level is never reached (must fix; 1 data line, 2 faults lines)

For data nested five third-party levels deep whose fifth level holds unrecognized data, your tool gives not-encodable ("an unrecognized inner packet has nothing to encode", via tool). The other five give invalid-third-party-header.

Rule: README, "an encoder refuses data nested deeper as invalid-third-party-header ... neither a decoder nor an encoder recurses past the fifth level"; interpretations, "It counts the levels as it goes and stops at the fifth, so it never recurses further than a decoder does". The undecoded data is never reached, so the stand-in rule for inputs the tool cannot hold does not apply to it.

Fix: count the levels first; past four, report invalid-third-party-header without looking at what is below.

3. A Mic-E comment that no form can write is text-reads-as-field, not does-not-read-back (must fix; 1 rbdata line)

Reproducer (encode mode):
{"n":100992,"data":{"type":"mic-e","mic_e_message":"en-route","latitude":51.5,"longitude":-0.5,"symbol":"/>","speed_knots":10,"comment":">5}"},"exact":true}
Straight on, ">" reads as a type code (comment "5}"); after "/", "/>5}" reads as a Mic-E altitude; after a space, the space reads as a type code. Today: refused does-not-read-back ("would read back as different data (type_code)"), the finding of the last form tried. Expected: {"result":"refused","refusal":"text-reads-as-field"}

Rule: README Read-back, "The refusal is the code of the named rule whose fault the read-back caught, where one does, text-reads-as-field when free text reads back changed, and does-not-read-back otherwise"; Refusal reasons, "free text that reads back changed is text-reads-as-field ... and anything else is does-not-read-back". The comment is the only thing that cannot be written. Fix: when every form fails, name the code from the first form tried (the comment as given), not the last.
