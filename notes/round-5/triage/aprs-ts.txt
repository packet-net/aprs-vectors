1. Pass-through writers refuse held packets that read back exactly as held (must fix)

packetToTnc2 / packetToAx25 (and the inner-packet writers) call checkReadsAsHeld -> readsAsHeld -> sameData (src/encode/readback.ts), which is compareData with the encoder's rounding allowance. For a compressed report it rounds the held value to the cs step even when the value was read from comment text that holds it in whole units: an RNG0034 in the comment (34 miles compared with 34.49), or wind written after a compressed position (358 degrees compared with 0, 103 with 104, 5 mph with 5.105). So data compared with itself fails, and you refuse not-encodable (also replacing ax25-cannot-carry where the path holds a q-construct). This is about 470 fuzz lines per seed (positions, objects, items), and every one of them fails compareData(held, held).

Rule (README Read-back): "A field's reading depends on its header only through a Mic-E report's destination ... nothing else in the data form reads the header", and only "a field paired with a header under which it reads as other data is refused as not-encodable". The same bytes under the same non-Mic-E destination read as exactly the held data. The allowance rounds "to the step of the form written", and the form written carries these values in whole units.

Fix: when the held data was decoded from the bytes being written, compare the read data with the held data exactly (neutral form, inner info diagnostics left out), with no rounding. If readsAsHeld is also used for packets the program built from data, round only to the step of the field the value is actually carried in, never by the report's compression alone.

2. Pending ruling A2: the inner packet of a five-deep nest

For a packet with five or more "}" levels, the decoder reads four and the fifth level is unrecognized with error:invalid-third-party. An inner packet taken out and read on its own decodes one level deeper, so its data differs from the held data at the bottom, and you refuse every inner level not-encodable. The other five write each inner packet as received. The rules do not settle this; the proposed ruling is "write as received" (the held field is compared down to the level the held data reached).
