# Review findings to fix: aprs-c (scripts and harnesses in /tmp/r4-review-aprs-c/)
1. HIGH. src/other.c:630-635: a third-party packet whose INNER header has a 17th path entry: the header parser raises implementation-limit, which is then rewound and the packet failed as invalid-third-party (an error in both modes). That is a different reading, which the capacity rule forbids. Repro: `N0CALL>APZ001:}SRC>APZ001,WIDE0,...,WIDE0:>hi` with 17 entries (repro1_inner_path17.sh). Expected: data unrecognized with error:implementation-limit (pdn_aprs__overflow). Audit every place a nested or inner parse can hit a capacity (path, capabilities, extras, field length, nesting) for the same rewind.
2. MEDIUM. src/encode.c:2702: the 4096-byte scratch array is in encode_info's frame on every call (frame 192 -> 6976 bytes; peak stack for one short pdn_aprs_build_position 14.7 KB on main, 21.4 KB now; repro2_stack.sh). Move the re-encode into a noinline helper used only when the caller's buffer overflows, so the common path costs no more stack than main; then measure and make README.md:253's stack figure true, and mention stack use in the CHANGELOG.
3. MEDIUM. tests/neutral.c:479: when pdn_aprs_decode_third_party returns anything but OK the dump tool writes `"packet": {}`, so an inner packet that hits a capacity appears as an empty packet with no implementation-limit and compares as a disagreement (repro3_dump_inner_limit.sh). The dump must report implementation-limit for the record.
4. LOW. tests/recipe.c:51 swaps NUL for 0x01 and the record is not marked "via":"tool". Mark it.
5. LOW. fuzz/fuzz_decode.c: assert that nothing an encoder or builder writes exceeds 256 bytes of information field, and fix the stale comment.
6. LOW. pdn_aprs_write_tnc2 and pdn_aprs_write_ax25 write a received field over 256 bytes as received. Ruling: pass-through writers of a decoded packet are not encoders and do not check. Say so in the README and CHANGELOG.
7. From the vectors review: publish the capacities machine-readably (limits.json at the repo root: information-field 512, path 16, capabilities 64, weather-extras 8, and any other fixed capacity the decoder has), and every implementation-limit dump record names its limit in a `limit` key. The test runner must FAIL, not skip, when a case gives implementation-limit for input within those capacities.
